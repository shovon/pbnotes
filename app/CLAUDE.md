# pbnotes

Electron + React + TypeScript, built with Electron Forge and Vite.

## Naming

The app's display name is **Pb Notes**: `productName`, the window title, and anything else a user reads. Its identifier is `pbnotes`: the package `name`, the executable, the `window.pbnotes` bridge, the `pbnotes-image://` scheme, the repo, and the `userData` directory, which `src/main/index.ts` pins so that it does not follow the display name.

## Positioning

The slogan is **"Local-first knowledge sharing and management, safe for many writers."** It is the same line in `description` in `package.json`, the first line of `../README.md`, and the GitHub repo description; change all three together or none.

What sets Pb Notes apart is that it is local-first, that many writers can share one folder through any sync tool without a conflicted copy, and that it is for knowledge sharing and management. "Project" is table stakes: it is the name of the primitive in the code and in the UI, but user-facing copy never leads with it or pitches the app as "notes for projects".

- Do not call it an outliner, a note-taking app or a project notebook. It can be used for outlining, but like Logseq and Roam it is a tool for thinking out loud, and a narrower noun undersells it.
- "Many writers" means many machines writing to one folder. Several people sharing a folder is where this is heading and already works that way, but it is not a front-and-centre feature: do not write copy that promises collaboration, authorship or presence.
- Do not claim "conflict-free" or "never loses an edit". There are no conflicted copies, but text is last-writer-wins per block.

## Before removing anything

The `projects` table and the `projects:*` IPC surface are **not** dead code, however little UI currently sits on top of them. They are the only record of which directories the user asked pbnotes to track; the filesystem cannot hold that choice, so deleting them loses it permanently. See "A list of folders the user picked" in `../DNA.md` before touching `src/main/features/projects/projects-*.ts`, `src/main/features/projects/open-project/`, `src/shared/projects.ts`, or the `projects` migration in `src/main/db.ts`.

## Storage boundary

Two stores, and they do not swap. SQLite holds the projects registry and config; the append-only event log in `@pbnotes/ledger` (`../packages/ledger/`) holds project content. Content is never moved into SQLite and the registry is never moved onto the log. A relational store as the system of record would fix the shape of the content forever, and the registry is bookkeeping that gains nothing from being event-sourced. See "The folder is the ledger" in `../DNA.md`.

A third store, the bench (one file per project, `userData/bench/<project-id>.db`), holds this machine's state that only means something to the product, such as recent pages. It is a convenience, never a record, and it is not `notes.db`: a table goes in `notes.db` only if it would exist whatever the product is. See "The bench" in `../DNA.md`.

**Content is written in the user's project folder**, which is the ledger itself (`LEDGER`, `AGENTS.md` and one directory per writer at its top), never under `userData`. The folder is the point: notes back up, sync and move with it, and losing the app's support directory must never lose a word the user wrote. `userData` holds `notes.db` and nothing else that matters: the bench is there too, and losing it costs only conveniences.

## Conventions

- For Markdown prose, use one line per paragraph, rather than hard-wrap. Most developers viewing Mardown files are already viewing them in editors that support soft-wrap. And also, single-paragraph diffs look much nicer if we are not beholden to the 80 character limit
- Migrations in `src/main/db.ts` (`notes.db`) and `src/main/features/bench/bench-store.ts` (each bench file) are append-only, and `src/main/sqlite.ts` runs either list. Add an entry, never edit a shipped one; `PRAGMA user_version` counts what has been applied.
- `src/shared` is bundled into the renderer as well as main — types and constants only, no `node:` imports, and nothing imported from `src/main` or `src/renderer` (lint enforces it). Pure functions both sides have to agree on (the block fold, the tree walks, the link parser, `today`) are `@pbnotes/graph`, not `shared`.
- The ledger is `@pbnotes/ledger` (`../packages/ledger/`), a workspace package: plumbing that knows no event's meaning, imports nothing but Node builtins, and is reached only by its package name, never a relative path. It opens one folder, which is the project folder. Which folders are open, and the fold over each, are the app's: `src/main/ledgers.ts` keeps one `Ledger` per project id (reopened when the path changes, dropped when an open fails) and paces them all by whether a window has focus (`setFocused`, wired in `index.ts`; the numbers are "Cadence" in the spec), and `index.ts` passes the project itself as the `LedgerRef`. There is no device identity to keep: the app's `ledger.writer()` gets a directory of its own under a fresh id (#45). `openWriter` (#61) is the other way in, for short-lived writers: it resumes one directory per key, boot, user and folder under an OS lock. Outside main (`src/shared`, `src/renderer`, `src/preload`) the package is `import type` only, and lint enforces it; `src/shared/log.ts` re-exports the status types for the renderer.
- Main has two parts. `src/main/features/<name>/` holds one subject each (`projects`, `window-state`, `bench`, `sidebar`). The shell (`db.ts`, `sqlite.ts`, `ledgers.ts`, `ipc.ts`, `index.ts`) is not a feature and stays loose in `src/main/`. A shell module that gets a unit test stays loose too, with the test beside it (`ledgers.ts`, `ledgers.test.ts`): the folder-per-tested-module rule under "Encapsulate by folder" is for features and views, not the shell.
- Every entry point is a composition root: `src/main/index.ts`, `src/renderer/index.tsx`, the CLI, and each test file. State and I/O (the database, the ledgers, the disk, the displays, the clock, randomness, the platform, `window.pbnotes`) are made there and handed down; no module keeps a handle at module scope or reads `process.platform`, `new Date()` or `randomUUID()` for itself. Main's modules are factories over what they are given (`openDatabase(file)`, `createDisk()`, `createProjectsStore(db, { disk, now, newId, pathKey })`, `createWindowState(db, workAreaFor)`, `createLedgers()`, `createOpenProject(store, probe, onMoved)`, `createGraphSession(open, notify)`), and renderer views take the bridge and the clock as props. A module that is handed something declares only the part it calls: the store's `Disk` and `open-project.ts`'s `Probe` are both met by the one `createDisk()` in `index.ts`, and a test hands each a disk of its own; `window-state.ts` takes a `TrackedWindow`, which a `BrowserWindow` is as it is, and `workAreaFor`, which `index.ts` builds from `screen`. An IPC file is only its channels: `registerProjectIpc(store, openProject)` and `registerGraphIpc(session, images)` check what arrives and hand it to what they were given, which import nothing from `electron` and run under `node --test`. Only what Electron alone can do (dialogs, `shell`, menus, the image scheme, sending to windows) stays in the IPC file. `@pbnotes/graph` reads no clock and no randomness: `today(now)` takes the date and `addBlock`/`blockCreated` take the block id. The rules behind this are the `bunnyhug` skill in `../.claude/skills/bunnyhug/SKILL.md`.
- The project is the top primitive, so `features/projects/` holds the registry (`projects-store.ts`, `projects-ipc.ts`, `open-project/`, and `disk/`, the one place in it that touches the filesystem) and everything a project contains nests under it (`graph/`: the pages and blocks it holds). Main holds which project is open (`open-project.ts`), set by `projects:open`; no other channel carries a project id. What a project contains does not know it is in one, or that it is kept on a ledger: `graph/` imports nothing from `projects-*.ts`, `open-project/`, `shared/projects.ts`, `ledgers.ts` or `@pbnotes/ledger` (test files aside), and never sees a project id, a ledger id or a path. `index.ts` hands the session what is open (`Open` in `graph-session.ts`): `require`, which resolves to its view of the graph fold (`GraphView`: `state`, `version`, `status`, `dispatch`). `graph-session.ts` declares that type, as the one that uses it; `ledgers.ts` declares its own (`LedgerView`) and imports nothing from `graph/`, and `index.ts`, where the two meet, is where the compiler checks one is the other. Images write no event, so they skip the session: `index.ts` hands `registerGraphIpc` `Images` (`save` and `find`, declared in `graph-ipc.ts`), built from the open project's path and this session's writer directory (`writerOf` in `ledgers.ts`). `index.ts` is the one place that says any of that is the open project's. `require` and `save` go through `requireProject` — the check that stops a write to an unmounted drive — which settles which project before its first `await`, so a handler calls them first and a write sent just before the project changed lands where it was typed. `find` goes through `currentProject`, so reading an image never opens or creates anything. Changes are wired the same way: `index.ts` makes the one `onChange` call (`ledgers.ts`; it fires for a write of ours, for an arrival from another session, and when the fold catches up with a write of ours) and tells each feature through the function it exposes (`refreshPages` in `graph-session.ts`), after checking that the project that moved is the open one — a feature is never handed an id to compare — so `projects-ipc.ts` and `open-project.ts` import nothing a project contains. `onChange` holds one listener, so a second caller replaces the first. A change of which project is open is wired the same way again: `createOpenProject` takes one callback, `index.ts` passes what a feature exposes for it, and the callback is told that the open project changed and not which. It is for a feature that holds something per project in main; the graph holds one thing of the kind, undo's history (the trail is the window's), and the callback lets go of the open project's bench file and calls the session's `forget`. A new feature that lives in a project exports its fold, and gets a fold run over the ledger in `ledgers.ts`, a `create…Session(open, …)` and a `register…Ipc(session)` call in `index.ts`, and a line in the `onChange` listener (and in the project-changed one, if it holds something per project in main); nothing in `projects-*.ts` changes.
- Events are folded into the view in main only (`ledgers.ts`, through `Ledger.onFold`). The renderer never replays the log and never holds a fold of its own; the one thing it folds is its own writes still in flight, with main's reducer, over the view main last answered with (see the next point). Reducers stay pure, over structured-cloneable state, so the fold can move to a worker later.
- Main holds the data and the fold; the renderer holds where it is and asks for what shows there. The trail of places followed is the window's own: `ProjectView` holds it and steps it with the pure `go`, `home`, `browse`, `back` and `rezoom` in `src/renderer/project/trail/` (a journal stop is `undefined`, as the journal is everywhere else, and the All pages list is `ALL_PAGES`; `placeOf` turns either into no place), so each window has its own, and `App` remounting the view per project starts it over at the journal. Main answers one query, `graph:view` (`view` in `graph-session.ts`, `getView` in `graph/place-view/`): what shows at one place, or the journal with the window's today on top, as a `PlaceView` in `src/shared/graph.ts`, labelled with the fold version it was read at. The version is `ledgers.ts`'s: one counter that goes up every time any fold changes, a write of ours and an arrival alike, read beside the state with no `await` between them, so a view at version `n` holds every change up to `n` and none after. `graph:changed` carries only that version, and goes out whenever the fold moves, whoever moved it; each window, on hearing it, asks again for its place (`heard` in `src/renderer/project/fetcher/`), and keeps the answer with the highest version for the place it is on, ignoring one older than it holds or for a place it has left (`held/`). A write's reply means the write is recorded, and carries the version it led to. The renderer keeps only what lasts as long as a gesture: the text in an open box, the caret, focus and scroll, and where it is. The one thing it draws ahead of main is its own writes in flight: `PageView.tsx` keeps each as the event it will be recorded as, built by the same builder main's command writes it with (`blockEdited` and the rest, each paired with the `run` command that sends it in `PageView/steps/`), and draws the page through `predict` in `@pbnotes/graph`. A prediction is dropped once a view at its write's version has arrived (`PageView/pending/`): tagged with the version its reply named, drawn over any older view, and dropped at once when the write is refused or its reply names no version. Every change, this window's or not, reaches the screen the same way, so arrival order does not matter and nothing is held until a notice is heard. A reply that names a version above the view held, with no fetch on its way that will reach it, asks once for the place: the net under a notice that was lost. A prediction uses main's `reduce` and main's `indented`/`outdented`, never a second copy of either. For that to work the renderer names a new block (`crypto.randomUUID()`, checked by main before it reaches the log), and `write` in `graph-session.ts` records writes one at a time in arrival order, so a write may name a block the one before it is still writing. The renderer may hold the view it asked for, never a fold of its own: do not send it the fold, and do not have main track which place each window is on.
- A project has one ledger, and a feature reads and writes it through a fold of its own. The feature exports the fold as a plain object, `{ reduce, initial }` (`graphFold` in `@pbnotes/graph`), and `ledgers.ts` runs it over the ledger with `onFold`. Never call `openOrCreate` on a project's folder anywhere else: `ledgers.ts` holds the one `Ledger` per project, and with it the one writer. A write's reply follows the state it led to: `dispatch` in `ledgers.ts` folds the event `post` returns into the held state, moves the version and announces it before it resolves, so the version the reply names already holds it and the renderer never drops a prediction main does not yet hold. Later yields from `onFold` are the truth once they reach every write `dispatch` folded in itself; one short of that (`reachOf` the write's event) was folded before the write was in the log and is skipped, since taking it would drop the write under a version that claims it (#170). If a yield taken already reaches the write, `dispatch` does not fold it again. Either way the version moves only to a state that holds everything the one before it held.
- There is no way for a feature to iterate the log, and none should be added. A feature that needs the events themselves has its reducer push each one onto an array in its own fold state and reads them from there; the second copy in memory is fine.
- Every fold is handed every event. A reducer returns the same `state` object for an event that is not its own, and never throws: one fold throwing fails the open for the whole project. The ledger gates nothing, so the version gate is the fold's: `graphFold.reduce` returns `state` for a type not in `HANDLES`, a bare name, or a `v` above what `HANDLES` says it reads, and the builders (`blockCreated` and the rest) write the `v` from the same table. Event type names are shared across features, so each starts with its subject (`block.*`). Every pbnotes event type is written and read under a namespace, `github.com/shovon/pbnotes#block.created` (`NAMESPACE` in `@pbnotes/graph`, public contract since #54), and has no other name. The first logs held bare names (`block.created`). Those were rewritten on disk once (#39), and the code that did it is gone (#40): a bare name is not folded. Do not add a bare name back to `HANDLES` or to `reduce`, and do not bring the rewrite back. A build from before #37 skips a namespaced event, so it cannot share a folder with this one. The namespace is an identifier, not a link: never change its bytes.
- One IPC channel, one feature, one `ipcMain.handle` handler. Fan-out happens in the ledger, not on the channel: a feature that cares about another feature's write folds that event in its own reducer, which also covers events arriving from other devices. Never attach a second handler or sub-handler to a channel, and never move to `ipcMain.on` to get one — a reply has one owner, and a write that half-succeeds across two handlers reaches the renderer as one rejection. A channel may carry a tagged union of commands, checked and routed by its one handler, as long as each message runs exactly one command and has one reply: every graph write is a case on `Command` in `src/shared/graph.ts`, sent over `graph:command` through `run`, checked by `requireCommand` (`features/projects/graph/command/`), and run by the session's `run` (#158). A new write is a case on `Command`, a checker beside it and a case in the session's `switch`, not a channel of its own. Every write `run` records is also kept as a step for undo (#234): `features/projects/graph/history/` holds them, up to 1,000, per graph view and in memory only, each as the events it wrote and what `remember` in `@pbnotes/graph` gives, never a graph. `undo` and `redo` are cases on `Command` too, and answer with an `Undone` rather than a bare version: undo stops, never skips, at a step someone else changed or that cannot be undone, and redo writes the step's own events again. In the window (#247), the browser's own undo is never used: the app's menu (`features/menu/`, Electron's default but for Undo and Redo) sends `graph:take` to the focused window, and `ProjectView` hands it to one dispatcher (`project/undo/`), which asks the open field's own history first and main's second. A text field opts in with `data-undo="document"` (a note field, whose undo goes on to main's) or `data-undo="field"` (the search box, whose undo never does); `watchFields` keeps a history per element from the document, so a field needs nothing but the attribute, and one that changes its own text through `execCommand` says so first with `OwnEdit`. Main's answer decides where the window lands (#248, `project/undo/landing/`, pure): the step's page, its block flashed once the view holds the undo's version, and when undo stopped, the same plus a sentence in the app's notice, thrown through `act`; nothing to undo does nothing. Anything that is not a ledger event (a second read, a side effect outside the log) is a second channel the renderer calls separately.
- Log events are immutable. A payload shape that changes gets a new `v` and is upcast when read; the file on disk is never rewritten or compacted.
- The log is segmented per writer directory: `<project>/<writer-id>/0000000000000001.log` upward, sixteen digits so text order matches numeric order. Only the newest segment is written to, and `seq` keeps counting across them _within that directory_, including across a resume. Directories from before #50 are named by device id and read as writers that have stopped. Sealed at 16 MiB or at local midnight, whichever comes first.
- **One writer per directory at a time, resumed from what is on disk (#61).** A writer appends only inside its own directory, and the ledger enforces that no two write one directory at once. The only file required at the top of a project folder is the `LEDGER` marker, which every machine writes with the same bytes, once. Anything else a build adds there follows "What else the folder may hold" in `packages/ledger/multi-writer.md` (#104). One exception: the marker's comment line changed in #50 ("one writing session" for "one device"). Both builds skip comment lines and accept either file, but two machines on different builds that create the same folder before they sync write different bytes and get a conflicted copy. This is what makes the folder safe in Dropbox, and it is not negotiable — two machines on one path is how the folder loses notes silently.
- Images are stored per device and linked without one: a paste writes `<project>/<session-id>/images/<sha256>.png`, the block says `![](images/<sha256>.png)`, and main looks in every directory's `images/` for the name, so images under an old device id still resolve. The storing and the lookup are `@pbnotes/files` (`../packages/files/`), which, like the ledger, imports nothing from the app, and neither package imports the other; `src/main/features/projects/graph/images/images.ts` holds only what is about images: the types taken, the folder name and the link form. The hash name is what makes that safe — the same name is the same bytes — so never store an image under a name that is not its hash, and never in a shared folder at the top of the project.
- A ledger opens through `openOrCreate` in `@pbnotes/ledger`, and that is the one way one comes to exist: a missing or empty folder (dotfiles such as `.DS_Store`, and named extras such as `AGENTS.md`, aside) is made a ledger, and everything else that is not already one is refused and offered nothing, an unmarked one (segments, no marker) included. Never `mkdir` a ledger or write a `LEDGER` any other way, and never add a way to force past a refusal. The marker's signature line is on disk forever: do not change it. The ledger reads every directory at the top as a writer directory.
- `seq` detects damage within a device. Ordering across devices is the hybrid logical clock (`hlc`), floored by what has been seen and bounded against a clock set to the wrong year. Never order by `at`; it is for display.
- Never truncate, rewrite or repair a file belonging to another device. A half-arrived foreign log stalls and retries; it must never stop a project from opening. See `../packages/ledger/multi-writer.md`, the ledger's spec.
- What events mean is `@pbnotes/graph` (`../packages/graph/`), a workspace package so that other programs reading a folder fold it the same way the app does (#54): the event schema, `NAMESPACE` and `HANDLES`, the fold and its gate (`graphFold`), the queries over it, which take the fold state alone and resolve a title to the page it opens first (`getPage`, `getPages`, `getReferences`, `getPreviews`, `getProperties`, `getTags`, `getTaggedBy`, `getAliases`, `getAliasOf`, `resolve`, `getDeletions`, `getRefsTo`, `getEdited`, `searchPages`, `searchNames`, `listPages`, `locateBlock`), one pure builder per event (`blockCreated`, `blockEdited`, `blockDeleted`, `blockIndented`, `blockOutdented`, `blockMoved`, `propertySet`, `propertyRemoved`, `tagAdded`, `tagRemoved`, `aliasAdded`, `aliasRemoved`, `pageDeleted`, and `batch`, which holds several of the others as one record), and the commands that check against the fold, build and dispatch (`addBlock` and the rest). Every event is one module under `src/events/` in that package, grouped by subject, holding its name, `v`, payload reading, fold, builder and undo; its `README.md` is how to add, change or remove one, and an event a log may hold is never removed. Undo's pure half is there too: `remember` (a step as the events that undo it, or `undefined` when it cannot be undone, and the readings of what it touched, with no graph kept), `holds` (whether a remembered step can still be undone) and `invert` (the events alone), over `UNDO`, built from each event's own undo; the history is the app's. It imports no `node:` module, since the renderer bundles it, and never `@pbnotes/ledger`: the fold takes `{ type, v, payload }` and the commands write through `GraphView.dispatch`. What stays in the app is what belongs to the window, the clock or the log: `getView` (`graph/place-view/`), the `status` and `version` on the app's `GraphView` (`graph-session.ts`), and the IPC contract in `src/shared/graph.ts`, `Command` among it. Reach it by its package name, never a relative path.
- Selecting blocks (#253) is the window's, like the trail: `ProjectView` holds one selection over every `PageView` it draws (journal days and linked-reference cuts alike) and hands it down through the `Selecting` context. It selects places, not blocks: each place a block shows has its own key (`slotKey(scope, id)` in `project/selection/shown.ts`, a cut's scope nested under its page's), and the order is read off the screen's `[data-slot]` elements. The selection algebra (`selection/`), the keys (`selection/shortcut/`) and `roots` (`selection/roots/`, the top-most selected blocks, once per id, what anything acting on a selection takes) are pure and know nothing of blocks or the DOM. `roots` sees only what shows, and a cut shows a block without its parent, so whatever acts on a selection checks against the graph. Acting on a selection is `ProjectView`'s too, since it can span page views: Delete and Backspace (#258) send one `deleteBlocks` of the roots' ids, which main resolves against the graph and writes as one batch, and a selected dot's menu does the same through the context (`deleting`, `removeChosen`). It is not drawn ahead of main. Dragging across blocks selects them too (#262): `selection/sweep/sweep.ts` is the arithmetic over rows (pure), `selection/sweep/watch.ts` the window's mouse and key events, and `ProjectView` says where a press may start (inside the page or on the blank around it, never on a dot, a link or a control) and turns a sweep into `span` over what was there to keep.
- The renderer reaches main only through `window.pbnotes`; keep new surface behind the context bridge in `src/preload/index.ts`.
- Each component should have an associated story in Storybook.
- Encapsulate by folder
  - Storybook stories and components should remain in the same folder
    - Component B used by component A, and by no one else: safe to place component B's folder inside component A's.
  - A module with a unit test gets a folder named after it, holding both: `src/main/features/projects/graph/trail/{trail.ts,trail.test.ts}`. The same nesting rule applies — `window-bounds` is only used by `window-state`, so it lives inside it. A module with no test stays a loose file until it has one.
- `@pbnotes/files` is for immutable, hash-named files only. Anything that changes is an event on the ledger, never a file beside it: two devices would each hold a copy with no order between them.
